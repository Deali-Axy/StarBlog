## 原始研究方案（2026-11-05，历史参考）

以下保留最初研究时的观察、设计建议和模型服务调研结论，不代表当前实现状态或当前服务商能力。研究阶段只读分析了代码、开发库和本地生产合并快照，并查阅官方文档；该阶段未调用付费推理、未连接生产数据库、未生成或写入译文。后续执行结果以上文为准。

复核缺失清单可使用：

```sql
SELECT p.id, p.title, p.last_update_time,
       length(coalesce(p.content, '')) AS body_chars
FROM post p
WHERE p.is_publish = 1
  AND NOT EXISTS (
    SELECT 1 FROM post_translation t
    WHERE t.post_id = p.id AND t.language = 'en'
  )
ORDER BY p.last_update_time DESC, p.id;
```

## 研究时的实现与限制

1. `apps/api/src/StarBlog.Api/Modules/Content/TranslationOperations.cs`：标题、摘要、全文依次请求模型，直到全部完成才保存。已有译文在生成之后查询并覆盖，没有跳过已有译文的模式；应用层没有批次状态、分块检查点、输出完整性校验或针对限流的调度。SDK 自身的重试能力不能替代这些任务状态。
2. `ContentEndpoints.cs` 的 `POST /api/v1/posts/{id}/translations?language=en` 是同步接口，绑定请求取消；管理端“已提交英文翻译”的提示实际在整个请求成功后显示。网关模板 `deploy/gateway.conf.template` 的读取超时为 120 秒，长文经公网同步处理存在超时风险。接口也不限制为已发布文章。
3. `PostTranslationConfiguration` 已有 `(post_id, language)` 唯一索引，适合实现幂等插入，但唯一索引本身不能阻止当前服务覆盖已有译文，也不能避免两个请求都先消耗推理费用。
4. `tools/DataProc/src/Services/ArticleTranslator.cs` 已有“仅发布文章、跳过已有译文、重试、分段”思路，但项目仍引用不存在的旧 `StarBlog.Data` / `StarBlog.Infrastructure` 项目，使用 FreeSql 旧实体，不能直接用于新版 EF Core 数据库。
5. 旧工具逐篇串行，失败会重跑整篇；其 `TimeoutSeconds` 没有被翻译执行代码使用，所谓请求间隔实际在一整篇处理结束后等待。按标题正则、空行分段不识别代码围栏、表格和列表，不能直接照搬。
6. API 的通用后台队列基于内存 `Channel`，重启后无法恢复待执行任务。不能仅把几百篇文章塞入这个队列就视为具备可靠批处理。
7. 现有 `PostTranslation` 没有原文指纹和模型、提示词版本。原文更新也不会自动使译文失效。[迁移记录](../production-rollout.md)已指出 `514395100768e83a` 的原文与现存译文来源版本不同，应列入单独复核，避免与“缺失译文”混为一个自动覆盖任务。
8. 仓库内生产 Compose 没有注入 `Translation__LLM__*`，API 的常规配置文件也未提供翻译连接。生产是否通过其他方式配置尚未核验，不能假设后台按钮已经具备可用模型连接。

## 推荐的第一阶段

新建独立命令行工具（例如 `tools/StarBlog.Translate`），使用新版契约。不要为这次补齐先恢复整个旧 DataProc，也不必先引入 Redis、完整任务平台或复杂管理界面。

### 1. 生成任务清单

- 读取最新生产一致性快照，只选 `is_publish = 1` 且不存在 `en` 译文的文章。快照只用于读取，不用开发库覆盖生产库。
- 清单记录文章 ID、语言、原文标题/摘要/正文、`sourceHash`、长度、优先级。`sourceHash` 对三个原文字段的确定性序列化计算 SHA-256，明确区分 null 与空字符串。
- 任务账本保存在工具专用 SQLite 或每任务独立结果文件中；与网站业务库分开。按文章、语言、原文指纹、提示词版本标识任务，记录待处理、成功、失败、待复核、已应用及每块结果。
- 现有译文即使疑似不完整也先进入复核清单，默认不覆盖。

### 2. 先试译 10 篇

样本覆盖普通技术文、生活文章、含代码/表格/图片的文章，以及至少一篇长文。记录实际输入/输出 Token、耗时、限流、失败率和人工审校结果，再决定模型与并发。优先复用已确认可用的服务，不因示例或 SDK 默认值自动更换模型。

### 3. 减少模型请求

- 普通文章一次返回 `title`、`summary`、`content` 的 JSON，约从每篇 3 次降至 1 次。406 篇对应约 406 次基础请求；长文分段及重试另计。请求数下降不等于 Token 成本也下降三分之二。
- 根据输入 Token、预计英文输出与模型最大输出预算决定是否分段。12,000 字符只能作为初步分流参考，不作为硬性安全阈值；这批有 13 篇超过该值。
- 长文按 Markdown 块结构拆分，每块记录独立结果、仅重试失败块，使用统一术语表和标题上下文保持一致。保留原始块间分隔，不简单用空行切分代码围栏、表格或列表。
- 通过 Markdown 解析器识别代码块、行内代码和链接/图片目标，采用可逆占位或原始片段保留方式保护。优先利用原始位置，避免 AST 重序列化无意改写全文。占位恢复需校验数量、唯一性和完整性。
- 提示词要求忠实翻译、保持语气、不补充新事实，并明确文章正文属于待翻译数据。模型返回的文章 ID、语言、路径等不作为写回依据。
- JSON 必须在本地按字段及类型校验；不能把 OpenAI 兼容等同于所有模型都支持 JSON Schema 严格输出。

### 4. 小并发、可恢复执行

- 首轮从并发 2 开始，根据实测 RPM/TPM 调整至 3–4；它是初始参数建议，不是已验证吞吐量。长文采用更低并发，写入结果由单写入器处理。
- 对 429、暂时性网络错误及可重试的服务端错误使用有上限的指数退避和随机抖动，优先尊重 `Retry-After`。鉴权、余额和参数问题应停止或挂起批次，避免重复付费请求。
- 每次请求有独立超时，成功立即保存响应和用量；恢复时复用已完成结果。不能在等待模型时持有业务数据库写事务。
- 支持限制文章数、Token/费用预算与取消；预算达到上限后保留进度。
- 账本防止两个进程重复领取同一任务；网络请求结果未知时记录为待核实。没有服务商幂等保证时，不能承诺崩溃恢复绝不重复计费。

### 5. 校验后经 API 写回

建议新增鉴权导入接口，例如 `PUT /api/v1/posts/{id}/translations/{language}`，只负责接收已生成译文，不调用模型。它是新能力，当前路由中不存在。

- 服务端复查文章仍存在、仍发布、原文 `sourceHash` 未变。原文已变返回冲突，旧结果留待重译。
- 默认仅在译文不存在时插入；同内容重复提交返回已存在，不同内容返回冲突。并发插入通过唯一约束及冲突处理保证不覆盖。原文检查和写入必须在同一个短事务中完成。
- 入库前校验字段、非空正文、完整结束标记/停止原因、JSON、代码片段和图片/链接目标；保留图片的原始路径，由现有前台渲染逻辑处理。
- 非法输出、缺块、代码或链接变化不得入库。篇幅异常、明显残留中文等作为复核信号，不能仅凭长度比例或中文占比判定技术文翻译失败。
- 每篇完整合并并通过校验后一次保存，避免只有标题或半篇正文的译文被公开读取。当前读取逻辑只要存在译文行就会使用其正文，并不为缺失正文逐字段回退。
- 写回记录新增译文 ID 和内容指纹，便于仅撤销本批且未被后续编辑的记录；不得用整库恢复撤销一批译文。
- 前台文章、列表和译文目录配置 300 秒缓存重验证；API 成功后页面可能要在下一次重验证后才显示，验收时分别检查 API 和网页。

建议工具提供 `plan`、`generate --limit 10`、`resume`、`validate`、`apply --dry-run`、`apply` 等子命令。先把任务状态放在工具侧；若以后要在后台常态运行，再增加持久任务表、领取租约、进度与取消接口，并让 HTTP 提交返回 202。

## 模型服务与 Batch 的选择

本地旧 DataProc 的私有连接配置指向 MiMo 新加坡 Token Plan，模型名为 `mimo-v2.5-pro`；这不代表生产 API 使用相同配置，也没有验证该模型当前是否仍可调用。本次没有使用配置中的密钥。

| 方案 | 适用情况 | 当前判断 |
| --- | --- | --- |
| 脚本逐篇调用现有翻译 POST | 极少量补译，追求最少改动 | 实现快，但仍是每篇 3 次模型请求、同步超时、缺少写前校验和防覆盖，不作为几百篇补齐的主方案 |
| 独立工具 + 常规推理 + 导入接口 | 希望尽快完成，保留模型选择灵活性 | 推荐先实现，立即支持试译、限流、断点和质量门禁 |
| 服务商 Batch + 同一导入接口 | 不要求实时完成，使用支持的模型及按量付费账户 | 作为生成端可选适配，不替代任务账本、校验和幂等写回 |

截至查询日，[MiMo 官方 Batch 文档](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/text-generation/batch-api)列出 `mimo-v2.6-pro` / `mimo-v2.6-flash`，价格为对应实时 API 的 50%；使用普通 API Key、从账户余额扣费，与 Token Plan 额度不互通，采用闲时调度。因此不能把本地 `v2.5-pro` 的 Token Plan 配置直接改成 Batch，并据此认定节省一半现有套餐成本。

[MiMo 结构化输出文档](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/text-generation/structured-output)目前列出的也是 v2.6 系列支持模型，提供 `json_object` 模式，字段结构仍需本地校验。本地 v2.5 配置的相同能力须通过小样本验证。

如果另选 OpenAI，官方 [Batch API](https://developers.openai.com/api/docs/guides/batch)支持异步 JSONL 任务、相对同步请求 50% 折扣和 24 小时处理窗口；这是 OpenAI 服务能力，不能据此推断任意 OpenAI 兼容网关也支持。

费用按试译实测的输入、缓存输入、输出及推理用量，结合最终服务商、模型和账户类型计算。没有取得这些数据前不报总价，也不把请求数或字符数当成 Token 计费量。

## 实施顺序与验收

1. 先实现只读清单、结果文件、生成器和校验器；获得最新生产快照后试译 10 篇，输出实际耗时、Token 和质量报告。
2. 增加服务端幂等导入能力；在隔离数据库验证重复提交、已有译文冲突、原文变更、并发导入、草稿/删除及无效译文均被正确处理。
3. 完成试译抽查后按优先级补齐余量：精选/近期文章优先，然后覆盖普通文章和长文。保留已有 275 篇，已知原文变化单独复核。
4. 最终按最新清单核对成功、失败、跳过、冲突、待复核的总数；确认已有译文未被覆盖、新增译文可读、英文目录和图片正常，抽查复杂 Markdown 与长文。
5. 再把经过验证的生成与保存逻辑提取为 API 可复用服务，用于新文章发布后的后台补译。后续记录原文指纹以支持过期识别，是否自动重译单独制定规则。

首轮必要验证集中在断点恢复、重复执行不覆盖、原文变更冲突、截断响应拒收、Markdown 代码/链接保留和长文重组；不为这次研究修改 API 或执行付费测试。
